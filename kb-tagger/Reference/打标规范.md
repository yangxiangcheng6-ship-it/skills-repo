# 打标规范（kb-tagger Reference）

## 三个元数据字段

| 字段 | 取值 | 说明 |
|------|------|------|
| version | `标准` / `偏离` | 文档版本，由用户提供或已知，**不自行猜测** |
| file_role | 7 类之一（下表） | 文档角色 |
| doc_summary | ≤15 字中文 | 一句话概括文档内容 |

## file_role 7 分类法

| 分类 | 判定依据 | 示例 |
|------|----------|------|
| **主协议** | 框架合同、Master Agreement、统领全局的总协议 | 主服务协议、框架协议 |
| **通用条款** | IT 采购的标准法律条款、General Terms | 标准通用条款与条件 |
| **数据保护附件** | DPA、数据处理协议、委托处理协议 | 数据保护附件（DPA） |
| **信息安全附件** | IT 安全最低要求、信息安全标准 | 信息安全附件 |
| **合规附件** | 行为准则、Code of Conduct | 合规行为准则 |
| **变更协议** | 对标准条款的偏离/变更/修改申请表 | 偏离申请表、变更协议 |
| **商务附件** | 报价单、价目表、价格清单 | Quotation、Price List |

## doc_summary 规范

- **15 字以内**（中文计数）
- 概括"文档是什么"，不是文件名、不是结论
- 好例：`IT采购通用条款与条件`、`委托处理个人数据协议`、`供应商信息安全最低要求`
- 坏例：`Appendix B`（文件名）、`重要合同`（无信息量）

## 打标流程要点

1. 先路由（version × 扩展名）拿到 KB 与字段 ID
2. 检索文档内容片段（hybrid_search，top_k=5，按 document_name 过滤）
3. LLM 按 7 分类法判断 file_role + doc_summary（version 已知不判断）
4. 构造 payload：`partial_update=true`，字段顺序 version → file_role → doc_summary
5. 校验（validate_tags.py）后提交 `POST /v1/datasets/{dataset_id}/documents/metadata`

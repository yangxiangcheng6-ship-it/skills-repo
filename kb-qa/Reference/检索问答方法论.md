# 检索问答方法论（kb-qa）

> 本文件是 k5 chatflow（`D:\夸克\k5.yml`，42 节点）主链路的设计沉淀。k5 的差异化对比链另见 diff-expert 的 `Reference/对比链方法.md`。

## 链路结构

```
文档清单(doc_list) → LLM 文档匹配(results[]) → 逐项检索(迭代) → 合并切片 → LLM 回答
                                              ↘ 匹配不到/无结果 → 澄清兜底
```

## 关键设计

### 1. doc_list 是"门牌号"
- 首轮从两库 API 拉文档清单，格式 `[KB名] doc_type值 | 摘要 | 文件名`，一次拉全（limit=50）
- LLM 匹配文档依赖它；检索无结果时的兜底也靠它（列候选让用户选）——所以首轮必拉，失败要如实报错

### 2. 检索词重写（最容易翻车的环节）
- query 必须去掉"标准/偏离/哪个版本"等筛选词，保留内容关键词
- **禁止用文档类型词当检索词**："通用条款""主协议"是分类不是主题，用了会检索不到具体条款（反例：query="通用条款"是错的，query="付款期限"才对）
- 具体条款用原文标题词（"合同文件""服务费用和付款"）
- 对比类问题所有组输出相同核心词（"付款期限"），禁止一组文档类型词、一组主题词
- 追问时合并检索词：`新query = 原query + 追问词`（k5 代码执行 5 的逻辑）

### 3. 检索配置（实测参数）
- hybrid_search：bge-m3(ollama) 向量 0.7 + 关键词 0.3
- rerank：qwen3-rerank，top_k 8
- metadata 过滤：version（is 精确）+ doc_type（is 精确），用字段 ID（标准库 version=f937afe4，doc_type=c6d05c1e；偏离库 version=5c475579，doc_type=cc1c88f9）

### 4. 合并切片
- 去重（相同 content 只留一次）
- 每块标 `【库名 | 文档名】` 前缀再截 6000 字，多块用空行拼接
- 合并后为空 → 走澄清，不硬答

## 报错兜底（三种情况）

| 情况 | 处理 |
|------|------|
| 匹配不到文档 | 澄清：从 doc_list 列候选让用户选 / 请用户补版本或文档名 |
| 检索无结果 | 澄清：说明没搜到，请用户换问法或补充细节 + 列可选文档 |
| API 报错 | 如实说明错误，不编造；提示稍后重试 |

## 经典坑（k5 实测，2026-08-19/21）

1. **LLM 的 context 只有写 `{{#context#}}` 占位符才会注入**——提示词模板必须显式带占位符，否则 LLM 收不到切片内容，按旧规则瞎答"内容一致"
2. **匹配别名过宽会误命中**（如"违约责任"别名映射到 terms 后全篇 1.0 分）——检索词宁可保守
3. **评测教训（k5 评测 10 题 70%）**：
   - "xx修改了哪些条款"类问法被路由进对比链（答非所问）——检索问答类先确认意图归属
   - 检索词带文档类型词会检索退化（31400 答不出来）——query 重写规则要严格
   - "哪些/清单"类问题 LLM 会漏条目——回答规则必须"逐条列全"
